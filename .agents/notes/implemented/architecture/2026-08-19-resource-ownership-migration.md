# Agent Note: Resource ownership migration onto OwnerPrincipal

Status: implemented

## Problem

[The ownership foundation](2026-08-18-owner-principal-and-user-home.md) established `OwnerPrincipal`, `OwnershipService`, and `UserHome`, and explicitly deferred wiring DSH's existing user-owned resources to it: sessions, JSONL persistence, workspace, settings, credentials, attachments, storage-domain records, the projection cache, message feedback, spill, jobs, terminal, and the HTTP/RPC/WebSocket surface. Without that wiring, an authenticated multi-user Web deployment has no actual per-user isolation — every resource still behaves as the single-tenant original.

## Decision

Each resource wraps its existing capability with an owner check derived from `ownership.currentPrincipalOrUndefined()`, never from client-supplied ids. `SessionHeader.ownerUserId` is the one authoritative owner field: set once from the request/background principal at session creation, immutable afterward, and reconstructed on resume from the persisted header rather than any request input.

**`get()`/`list()`/`roots()` stay unfiltered but require an explicit `'trusted-internal'` marker; owner narrowing is a separate seam.** `SessionStore.get(id, access)`/`.list(access)` and `AgentRegistry.get(id, access)`/`.list(access)`/`.roots(access)` return every live session/agent in the process regardless of caller, because dozens of trusted-internal call sites (the persistence coordinator, title/checkpoint/projection identity checks, autonomous goal/schedule continuation, lineage checks on an object the caller already holds, and most `src/invariant.ts` companions, which do not even execute outside `vitest`) depend on that. `access` is a required parameter whose only valid value is the literal type `'trusted-internal'`: the compiler rejects any call site that omits it, so every one of these ~90 internal call sites carries a visible, greppable declaration of trust rather than inheriting it from a default. Two exported free functions — `ownedSession`/`ownedSessions` (`@deepseek-ai/dsh-session`) and `ownedAgent`/`ownedAgents` (`@deepseek-ai/dsh-agent`) — take a caller-supplied id (or nothing, for the list forms) and internally perform the same trusted lookup narrowed to the current principal's own, and are the one seam a caller resolving a client-supplied id for an authenticated request must use; a request-facing call site can no longer obtain a raw `Session`/`Agent` without either calling one of these four functions or writing the literal `'trusted-internal'` marker inline. Both fail closed when `ownership` is mounted but no principal is in scope (background/misconfigured execution), and pass through unfiltered when no `ownership` service is mounted at all (single-tenant/CLI has no owner concept). `packages/api/remotes/src/agent-lookup.ts`, `packages/feedback/message-feedback/src/index.ts`, `packages/session-query/session-query/src/corpus.ts`, and `packages/host/apiproxy/src/api-proxy.ts` call these at every point a request payload's `sessionId`/`parentSessionId` resolves to a live session or agent.

JSONL session persistence roots each owner's physical log tree under `UserHome.path('sessions')`, reusing `OwnershipService.resolveUserHome` — no second `userId → path` mapping. Exact lookup, `list()`, and `listSnapshots()` are owner-partitioned at the source (never a global scan filtered in JS), and `session-query-sqlite`'s FTS and exact-lookup queries carry `owner_user_id` as a SQL predicate for the same reason. `packages/api/remotes/src/agent-lookup.ts`'s cold-resume path (`inspectApiRemoteSession`) adds an explicit `isOwnedByCurrentPrincipal` check on the persisted header rather than depending solely on the composed persistence backend to enforce it.

`WorkspaceRegistry` keeps its existing durable design (one KV table, one order array) and applies `isOwned`/`isHeaderOwned` at every read; `prepareOwner()` loads one owner's persisted history lazily on first authenticated access instead of enumerating everyone's at boot. `settings-file` resolves each owner's document lazily per call, never at plugin startup (no request/auth context exists then). `credentials-local` splits into a deployment plane (`reserveDeployment(ref)`, resolved before any authenticated user exists, never satisfiable from a `UserHome`) and a per-user plane (a `UserHome`-rooted `application.yaml`); the inherited process environment is checked before the per-user layer in both `resolve()` and `describe()`, and `writeUser()` calls the same `assertUnshadowed()` guard `write()` does, so a per-user write can never silently shadow a deployment-supplied credential. `attachment-local` and `spill-local` route through `UserHome`-rooted directories the same way, with spill resolving the target session's *durable* owner (via `ownership.backgroundPrincipal` when no request principal is in scope) rather than the caller's own identity, so a background write never lands under the wrong owner.

`host/apiproxy`'s WebSocket event streams (`events.mux`/`events.host`) capture `streamPrincipal` at subscribe time and re-check `visibleSession`/`ownedAgent` on every subsequent pushed event, rather than broadcasting and relying on client-side filtering. Every cross-owner denial across every resource returns a uniform not-found — never a 403 that would disclose the resource exists.

## Alternatives considered

**Add `getOwned`/`listOwned` as instance methods on `SessionStore`/`AgentRegistry`.** This was the first implementation and it broke roughly a dozen existing unit test files across `host/apiproxy`, whose test doubles provide `ctx.sessions`/`ctx.agents` as bare `{ get: vi.fn(...) }` objects rather than real class instances — a new required method is invisible to a duck-typed mock, so calling it throws `is not a function` at runtime with no compile-time signal (`as never`/`as unknown as X` casts hide the gap). Free functions wrapping the unfiltered `get()`/`list()` need no new method on the mock and produce the identical security posture, so this repo's existing service-mock convention did not need to change.

**Make `ownedSession`/`ownedAgent` fail closed even when no `ownership` service is mounted at all.** Rejected: this breaks single-tenant/CLI compositions and every apiproxy unit test that boots real `SessionStore`/`AgentRegistry` without mounting ownership, and it duplicates a distinction the rest of the codebase already draws correctly (`WorkspaceRegistry.isOwned`, `session-persistence-jsonl`'s owner-root resolution): "no ownership service" means no owner concept exists, not "deny everyone."

**Require `ownedSession`/`ownedAgent` at every request-facing call site by convention alone, without a compile-time marker on the raw primitive.** This was the initial design and it under-enforced: `packages/subagent/subagent/src/list-children.ts`'s corpus builder resolved the raw `SessionStore` via `ctx.get('sessions')` (never `ctx.sessions`) and called `.list()` directly, a call-site shape that a grep for `ctx\.sessions\.list\(` does not match; the equivalent gap also existed in `host/apiproxy`'s `events.mux` connection-time baseline (which pushed a session-existence and background-task-content snapshot for every live session, unlike the ongoing listeners a few lines below it in the same handler, which did check `visibleSession`) and in `session-query`'s `SessionCorpus` (which narrowed persisted headers by owner but merged live sessions unfiltered). All three reached production review undetected by convention alone. Requiring the literal `'trusted-internal'` parameter turns every one of these into a compile error the moment `get()`/`list()`/`roots()`'s signature changes, which is how the remaining ~90 internal call sites were enumerated exhaustively rather than by pattern-matching source text.

**Guard the SQLite session-persistence backend with a startup-time mount rejection when ownership is enabled.** Rejected per an explicit production-scope decision: this deployment is file-based only, and `@deepseek-ai/dsh-session-persistence-sqlite` is unsupported/out of the production security surface entirely, not merely unenforced. The half-finished ownership columns that had been added to it were reverted rather than guarded, to avoid presenting a plausible-looking backend that was never meant to carry multi-tenant data. `session-query-sqlite` (a distinct package — a read/FTS index, not a persistence backend) mounts in both `packages/bundle/base` and `packages/bundle/web-app` with `openAt: never`, so its query path does not run at all under the default composition; see Deferred below for the gap in its *persisted-vs-live* owner scoping, which the SQL predicate alone does not close once a deployment overrides `openAt`.

**Build a dedicated owner-checked spill-read tool, or add read-time owner confinement to the generic filesystem capability.** Rejected/deferred: `SpillStore`'s Service Definition has only `saveText`; retrieval is a raw host path rendered into the model's own conversation and read back through the generic `read`/`grep` filesystem tools, which apply no read confinement of any kind for any resource today (`fs-sandbox`'s own documentation: "Reads always pass through — every mode permits reading"). Closing that is a first-of-its-kind capability decision belonging to the filesystem/sandbox boundary (A3/PR B), not a resource-by-resource ownership migration; this change scopes to owner-rooted spill *persistence* only.

## Deferred

`session-persistence-sqlite`: unsupported, out of the production security surface; production composition closure that keeps a multi-user profile from selecting it belongs to A3.

`session-query-sqlite`'s `_observeStable()` (`packages/session-query/session-query-sqlite/src/index.ts`) narrows its *persisted* snapshot listing through `_ownedSnapshots()`, but merges the *live* session store (`this.ctx.sessions.list('trusted-internal')`) with no equivalent owner filter — the same gap this migration closed in four other places (`packages/subagent/subagent/src/list-children.ts`, `host/apiproxy`'s `events.mux` baseline, `session-query`'s default `SessionCorpus`, `packages/workspace/workspace/src/index.ts`). Confirmed dormant under the default `openAt: never` composition (`packages/bundle/base`, `packages/bundle/web-app`) — the observation loop this method belongs to never runs unless a deployment overrides `openAt` to enable full-text search. Deliberately left unfixed here, not overlooked: closing it belongs to A3's preset/provider closure work by disabling the capability for any multi-tenant profile, not by adding an owner check to a SQLite backend this migration otherwise treats as out of the production security surface (see Alternatives above). A3 must not re-investigate this from scratch; the fix, if this package is kept reachable at all in a multi-tenant profile, is the same `ownedSessions(ctx)` substitution applied everywhere else in this note.

Spill *retrieval* confinement (Bob knowing a host path or model-rendered locator should get not-found): belongs to the filesystem/sandbox capability boundary, not this migration.

Future shared/system resources (a Translation/Paper Library/Notebook-style feature) are not assumed impossible by any check added here; the private-by-default semantics this migration establishes cover only the resources named above, and a future shared-resource model is a separate, explicit authorization decision.

## Consequences

Alice and Bob, authenticated as distinct `OwnerPrincipal`s, cannot read, list, or mutate each other's sessions, JSONL logs, workspaces, settings, per-user credentials, attachments, spill writes, projection cache rows, or message feedback, and cannot resolve each other's live agents/jobs/terminals through the HTTP/RPC/WebSocket surface, even supplying a real, guessed, or forged id. A client-supplied `ownerUserId` has no authority anywhere in this surface. Legacy pre-ownership records (no `ownerUserId`) are never adopted by a newly authenticated principal — they simply match no one. Deployments without an `ownership` service mounted (single-tenant/CLI) are unaffected; every check above degrades to pass-through in that mode, matching pre-migration behavior exactly.

`ctx.subagents.listChildren`/`listDescendants` (`packages/subagent/subagent/src/list-children.ts`) now narrow their live-session merge through `ownedSessions`, so `subagents.list`/`subagents.history`/`subagents.prompt` no longer enumerate or serve a foreign owner's subagent catalog or conversation content through a known or guessed `parentSessionId`/`childSessionId`; `subagents.history`'s live-child branch additionally narrows through `ownedSession` independent of the catalog check, so a future regression in one does not reopen the other. `events.mux`'s connection-time baseline (`session/subscribed`, `session/queue`, `session/jobs`) and `SessionCorpus` (`session-query`'s `listSessions`/`load`/`projectMany`, consumed by the model-facing `tool-session-query`) received the same fix for the same reason: both merged a `'trusted-internal'` live-session read into their result with no owner check, unlike sibling code paths a few lines away in the same file that already had one. `WorkspaceRegistry.readSessionHeader`'s live branch and `sessionKnown`'s live-liveness check (`attachSession`/`archiveSession`) were narrowed the same way — a live session's raw header (including its real `cwd`) is no longer disclosed, and a foreign owner's live session id is no longer accepted as a valid `attachSession`/`archiveSession` target merely because it is live in the same process. `downloads.sessionLog` (`packages/host/apiproxy/src/api-proxy.ts`) now checks the requested root's owner before calling `flushLiveSessionLog` at all — the flush helper itself intentionally keeps its minimal `{ sessions }` capability and has no owner concept of its own, so a foreign owner's live session can no longer be forced through an early durability flush merely because its id is known or guessed; the subsequent raw artifact read was already safe through JSONL's owner-rooted path, so this closes a side-effect gap rather than a data-disclosure one.
